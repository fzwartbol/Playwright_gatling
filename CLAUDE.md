# CLAUDE.md — Playwright → WireMock → Gatling → Tekton Pipeline

## Project Purpose
Record real application traffic with Playwright through a WireMock reverse proxy, then replay those
stubs with Gatling for load testing — all orchestrated by a single Tekton pipeline.

WireMock stubs the **app's downstream services** (external APIs, partner services, etc.).
Gatling hits the **real application**; the app calls WireMock instead of live dependencies.

## Key Commands

### Demo GWT Application
```bash
cd gwt-app
mvn spring-boot:run          # starts on http://localhost:8090
# Or build a fat JAR:
mvn package -DskipTests && java -jar target/gwt-app-*.jar
```

### Local End-to-End Test
```bash
# 1. Start the demo GWT app
cd gwt-app && mvn spring-boot:run &; cd ..

# 2. Start WireMock as recording proxy (proxies to real app's downstream)
docker run --rm -d --name wm -p 8080:8080 \
  -v "$(pwd)/wiremock:/home/wiremock" \
  wiremock/wiremock:3.5.4-alpine \
  --global-response-templating --verbose

# 3. Start recording → downstream at :8090 (demo: app IS the downstream)
curl -sf -X POST http://localhost:8080/__admin/recordings/start \
  -H 'Content-Type: application/json' \
  -d '{"targetBaseUrl":"http://host.docker.internal:8090","persist":true,"repeatsAsScenarios":false}'

# 4. Playwright drives app; app calls WireMock which proxies to downstream
cd playwright && BASE_URL=http://localhost:8090 mvn test -Dtest=GwtJourneyTest; cd ..

# 5. Stop recording — stubs written to wiremock/mappings/
curl -sf -X POST http://localhost:8080/__admin/recordings/stop
ls wiremock/mappings/

# 6. Gatling load test: hits real app, app calls WireMock stubs
cd gatling
BASE_URL=http://localhost:8090 GATLING_USERS=5 GATLING_DURATION=15 \
  mvn gatling:test -Dgatling.simulationClass=simulations.GwtJourneySimulation

# 7. Verify no unmatched requests
curl -s http://localhost:8080/__admin/requests/unmatched | python3 -m json.tool
docker stop wm
```

### Playwright (Java)
```bash
cd playwright
# One-time: install browser binaries
mvn -q compile exec:java -e -Dexec.mainClass=com.microsoft.playwright.CLI -Dexec.args="install --with-deps"
# Run journey test
BASE_URL=http://localhost:8090 mvn test -Dtest=GwtJourneyTest
```

### Gatling (Maven)
```bash
cd gatling
# Run the GWT journey simulation
BASE_URL=http://localhost:8090 mvn gatling:test -Dgatling.simulationClass=simulations.GwtJourneySimulation
# Clean and run
mvn clean gatling:test
```

### Tekton — WireMock pipeline (plug and play)
```bash
# 1. One-time cluster setup (RBAC + PVC)
kubectl apply -f tekton/rbac.yaml
kubectl apply -f tekton/pvc.yaml

# 2. Install tasks and pipeline
kubectl apply -f tekton/tasks/
kubectl apply -f tekton/pipeline-wiremock.yaml

# 3. Edit pipelinerun-wiremock.yaml — set these values:
#      loadtest-repo-url    this repo
#      app-repo-url         your app git repo
#      overlay-path         path to k8s manifests inside the repo
#      app-service-name     Service name that exposes the app
#      downstream-base-url  real downstream service WireMock proxies to during recording
kubectl apply -f tekton/pipelinerun-wiremock.yaml

# 4. Watch it run
tkn pipelinerun logs --last -f
tkn pipelinerun list
```

## Tekton Pipeline Topology

**Architecture — WireMock sits between the app and its downstream dependencies:**

```
Recording:   Playwright → real app → WireMock (proxy) → real downstream services
Load test:   Gatling    → real app → WireMock (replay) → [stubs, no live services]
```

Gatling measures the **real application's** throughput and latency. Downstream
services are served from recorded stubs so they are never hit under load.

**Pipeline steps:**
```
fetch-loadtest-repo  ──┐
                       ├──► record ──► load-test
deploy-wiremock     ──┤
deploy-app          ──┘
```

- `fetch-loadtest-repo`: clones this repo (playwright/, gatling/, wiremock/mappings/) onto the PVC
- `deploy-wiremock`: creates namespace, deploys WireMock as K8s Deployment+Service; mounts the same PVC so pre-committed stubs are immediately available
- `deploy-app`: clones the app repo, creates namespace, applies overlay, waits for rollout
- `record`: starts WireMock recording → Playwright drives real app → app's outbound calls captured as stubs → recording stopped
- `load-test`: Gatling drives the real app; app calls WireMock which replays stubs

**App overlay requirement** — route outbound calls to WireMock:
```yaml
# In your app's loadtest Kustomize overlay or deployment patch:
env:
  - name: DOWNSTREAM_SERVICE_URL
    value: "http://wiremock.loadtest.svc.cluster.local:8080"
```

**PVC requirement** — ReadWriteMany (RWX):
WireMock K8s pod and Tekton task pods mount the same PVC simultaneously.
Use a storage class that supports RWX: NFS, CephFS, Azure Files, AWS EFS, GCP Filestore.

## WireMock Auth Design

For JWT/XSRF apps, Gatling hits the real app login directly (no WireMock stub needed
for authentication). WireMock only stubs the app's downstream service calls.

### Token flow
1. Login: `POST /api/auth/login` → `{"token":"eyJ...","xsrfToken":"..."}`
2. Gatling extracts: `jsonPath("$.token").saveAs("jwtToken")` + `jsonPath("$.xsrfToken").saveAs("xsrfToken")`
3. Subsequent requests: `Authorization: Bearer #{jwtToken}` + `X-XSRF-Token: #{xsrfToken}`

## Gatling Simulation Conventions
- **Language: Java DSL** (Gatling 3.11.x). Source: `gatling/src/test/java/simulations/`.
- Package: `simulations`; extend `io.gatling.javaapi.core.Simulation`
- Static-import `CoreDsl.*` and `HttpDsl.*`
- `setUp(...)` goes in an instance initializer block `{ ... }`
- Use `.random()` feeder strategy (never exhausts, unlike `.shuffle()`)
- Per-VU session variables: `session.getString("fieldName")` in lambda bodies
- Checks: always assert HTTP status; add `substring("//OK")` for GWT-RPC responses

## Workspace / PVC
All tasks share a single `PersistentVolumeClaim` named `playwright-gatling-ws`.

## Environment Variables
| Variable | Description |
|---|---|
| `BASE_URL` | Application under test base URL |
| `GATLING_USERS` | Target concurrent users (default `10`) |
| `GATLING_DURATION` | Ramp duration in seconds (default `60`) |
| `DOWNSTREAM_SERVICE_URL` | WireMock URL (set in app's loadtest overlay) |

## Common Failure Modes
- **Simulation compiles but gets 0 requests**: check `BASE_URL` points at the real app, not WireMock.
- **Gatling OOM**: increase Maven heap with `MAVEN_OPTS=-Xmx2g`.
- **Tekton workspace not bound**: PVC must exist before `PipelineRun`; create with `kubectl apply -f tekton/pvc.yaml`.
- **WireMock pod can't read stubs**: PVC must be ReadWriteMany; check storage class supports RWX.
- **Namespace race**: `deploy-wiremock` creates the namespace first (idempotent `kubectl create namespace`); `deploy-app` does the same — both are safe to run in parallel.
